<objective>
Add three things to the Promos tab: (1) a "Total profit possible" headline, (2) a per-member "Mark used" button with undo, and (3) daily / weekly / monthly "profit available" numbers backed by a persisted per-promo, per-Denver-day max-profit record.

Purpose: Let each member see how much guaranteed profit is on the table for them right now, clear out promos they've already done, and see how much profit was available over time.
Output: a pure tested totals module, two new tables + migration, a data module, a mark/unmark server action, getPromos wiring, and UI.
</objective>

<design_decisions>
Where profit observations are recorded (owner asked the planner to choose and document):
- Recorded inside getPromos, every time any member loads the Promos tab, NOT in the scraper run. Reason: ranking needs cached odds + hedge books, which getPromos already loads; the scraper (src/ingestion/promos/run.ts, GitHub Actions) does not rank and src/app must not import src/ingestion (boundary test). This adds zero Odds API calls: it reuses the already-fetched cached events.
- To make the record group-level and identical no matter which member triggers it, the observation ranking runs rankPromoHedges over ALL active promos (used or not, any member) against EVERY usable hedge book (getHedgeBookKeys() with no argument, the same call the existing "no-books" branch already makes). So each promo's recorded number is "best guaranteed profit available anywhere", not one member's hedge-book subset.
- Storage: table promo_profit_observations keyed (promo_id, denver_date) with book_key and max_guaranteed_profit numeric(10,2). Write is a single multi-row INSERT ... ON CONFLICT (promo_id, denver_date) DO UPDATE SET max_guaranteed_profit = GREATEST(existing, excluded), last_observed_at = excluded. Repeat loads/refreshes can only raise a day's value, never duplicate it.
- Only profitable opportunities (guaranteed profit > 0) are recorded; unprofitable promos contribute nothing.
- Per member display: sum over observations whose book_key is in the member's own books. Marking a promo used does NOT remove it from these period numbers (they measure what was AVAILABLE, per owner); it only affects the live feed and the headline total.
- Known limitation (accepted, documented in a code comment): a day with no Promos-tab visits records nothing for that day.
- A failing observation write must never break the feed: wrap recordProfitObservations in try/catch + console.error (same spirit as WR-09/WR-10).

Mark-used UI: a small ghost "Mark used" button on each row, plus a collapsed "Used (n)" section (existing src/components/ui/collapsible.tsx) below the rows listing used promos with an "Undo" button each. No toast system exists in the codebase, so the Used section IS the undo path.
</design_decisions>
