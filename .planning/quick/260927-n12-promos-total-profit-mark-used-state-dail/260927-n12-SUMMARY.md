## Decisions Made

- **Owner scope change A** (mid-execution instruction): replaced the plan's collapsed "Used (n)" + Undo section with an inline `used: boolean` flag on every row -- a used promo never leaves its position in the feed/unprofitable list; its background becomes a green gradient and its "Mark used" button becomes "Undo". Still excluded from `totalProfit`; still counted in `availableProfit`.
- **Owner scope change B** (mid-execution instruction): factored profit-observation computation out of `get-promos.ts` into `src/db/promoObservations.ts` so it's callable from both the server action and a new standalone script, and added a moneyline-only refresh to the 8am Denver scrape run. This is a superset of the original plan's "record inside getPromos only" design -- getPromos still calls the same shared function on every load.
- `book_key` on `promo_profit_observations` is set only on first insert per day and never overwritten by the `GREATEST` upsert -- matches the plan's literal design decision (only `max_guaranteed_profit`/`last_observed_at` update on conflict).
- `recordCurrentProfitObservations` accepts an optional pre-fetched `activePromos` array so `getPromos` avoids a duplicate DB read; the morning script (no preloaded list) fetches internally.
- Missing `ODDS_API_KEY` in the morning job logs and exits 0 (never fails the scrape job); a blocked/errored refresh still proceeds to record observations from whatever is already cached.

## User Setup Required

**A new GitHub Actions secret is required before the morning-refresh step can run in CI:**

- **Secret name:** `ODDS_API_KEY`
- **Where:** GitHub repo Settings -> Secrets and variables -> Actions -> New repository secret (same repo that already holds `DATABASE_URL`)
- **Value:** the same Odds API key already configured as `ODDS_API_KEY` in the Vercel deployment's environment variables
- **If not set:** the new `npm run odds:morning-observe` step logs `odds:morning-observe: skipped (missing-api-key)` and exits 0 -- the scrape job itself is unaffected, but no moneyline refresh or profit observation will be recorded by the scheduled job (getPromos will still record observations opportunistically whenever a member loads the Promos tab with cached odds present).

**Database migration not yet applied:**

- Migration `drizzle/0006_promo_tracking.sql` (creates `promo_completions` and `promo_profit_observations`) was generated with `drizzle-kit generate` but **`npm run db:migrate` was not run**, per this session's constraints. The orchestrator must run `npm run db:migrate` against the live Neon database before this feature works end-to-end (mark-used and profit-observation recording will throw/fail against a DB missing these tables until the migration is applied).
