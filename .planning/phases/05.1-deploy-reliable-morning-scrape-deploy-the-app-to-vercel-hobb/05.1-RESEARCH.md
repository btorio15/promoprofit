## Summary

The deploy is low-risk: `npx next build` already succeeds locally on Next 16.3.6 (Turbopack, TypeScript passes, `scripts/**/*.ts` are included by tsconfig but do not break the build, no Playwright dependency exists, db/session code is lazy so no env is needed at build). Vercel needs no custom build settings; default Next.js preset works. The only code change needed for the cron to function is a **proxy.ts exemption**: `src/proxy.ts` currently redirects any request lacking the session cookie to `/login`, which would 307 Vercel's cron call (Vercel cron does NOT follow redirects, so the job would silently "complete" without dispatching).

Vercel Hobby cron facts (verified): 100 jobs per project, minimum interval once per day, precision per hour (fires anywhere inside the scheduled hour), no retries on failure, best-effort delivery with occasional duplicate invocations, expressions that run more than once per day fail deployment. CLAUDE.md's older "max 2 jobs" statement is outdated; irrelevant here since only 1 cron is used. The route is a normal App Router GET route handler; `CRON_SECRET` env var is auto-sent as `Authorization: Bearer <secret>`.

GitHub dispatch: `POST /repos/btorio15/promoprofit/actions/workflows/scrape-promos.yml/dispatches` with body `{ref:"main", inputs:{force_morning_observe:"true"}}`, a fine-grained PAT with repository permission Actions: Read and write. Current docs list HTTP 200 with run details (API version 2026-03-10); older versions return 204 - code must accept any 2xx. The simplest correct "already scraped today" check is a read of `scrape_runs` (already written every run, per book, with `status` and `ran_at`): no new table, no Odds API credits.

**Primary recommendation:** Add `src/app/api/cron/scrape/route.ts` (GET, Node runtime, CRON_SECRET check, `fetch` dispatch with `ref:"main"`, `inputs:{force_morning_observe:"true"}`), exempt `/api/cron/` in `src/proxy.ts`, add `vercel.json` with one cron `"23 13 * * *"`-style entry, add `scripts/already-ran-today.ts` + gated workflow steps for the single 15:37 UTC backup, and wrap the five unguarded call sites in `safeAction`.

### System Architecture Diagram

```

      {ref:"main", inputs:{force_morning_observe:"true"}}
   |-- 2xx --> 200 {dispatched:true}

        |-- observed today? -> skip morning-observe step
```

### Pattern 1: Cron route (verified against Vercel docs)
```ts
// Source: https://vercel.com/docs/cron-jobs/manage-cron-jobs
import type { NextRequest } from "next/server";
export const runtime = "nodejs";          // default; state explicitly
export const dynamic = "force-dynamic";   // never cache a GET handler result
export const maxDuration = 30;            // Hobby max is 300s; this call takes <2s

export async function GET(request: NextRequest) {
  const secret = process.env.CRON_SECRET;
  if (!secret || request.headers.get("authorization") !== `Bearer ${secret}`) {
    return new Response("Unauthorized", { status: 401 });   // fail CLOSED when unset
  }
  // ... dispatchScrapeWorkflow()
}
```
Use a constant-time compare (`crypto.timingSafeEqual` on equal-length buffers) rather than `!==`; guard length first.

### Pattern 2: GitHub dispatch
```ts
// Source: https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event
const res = await fetch(
  `https://api.github.com/repos/${repo}/actions/workflows/scrape-promos.yml/dispatches`,
  {
    method: "POST",
    headers: {
      Accept: "application/vnd.github+json",
      Authorization: `Bearer ${token}`,
      "X-GitHub-Api-Version": "2022-11-28",   // or 2026-03-10; behavior differs (204 vs 200 body) - accept any 2xx
      "User-Agent": "promoprofit-cron",       // GitHub REST requires a User-Agent
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ ref: "main", inputs: { force_morning_observe: "true" } }),
    cache: "no-store",
  },
);
if (!res.ok) { /* log res.status + (await res.text()).slice(0,200); never log the token */ }
```
- `inputs` values are sent as strings even for boolean workflow inputs ("true"); the workflow's existing expression `github.event.inputs.force_morning_observe == 'true'` already matches this form. [CITED: docs.github.com REST workflows; ASSUMED string coercion detail - verify with first manual dispatch]
- Constants (`btorio15/promoprofit`, `scrape-promos.yml`, `main`) as non-secret defaults, overridable via `GH_REPO`; token env var name `GH_DISPATCH_TOKEN` (avoid `GITHUB_` prefix to dodge confusion with Actions-reserved names).
- Rate limits: PAT 5,000 req/h primary; content-creation secondary limits 80/min, 500/h - one call/day is irrelevant. [CITED: docs.github.com rate-limits]
- Failures: 404 = wrong token scope/workflow name/repo (fine-grained token returns 404 for missing access) ; 403 = permission; 422 = workflow lacks `workflow_dispatch` trigger or bad input/ref. Dispatch only works if the workflow file with `workflow_dispatch` exists on the `ref` branch (main), so **the workflow change must be pushed before the first cron fire**.

### Pattern 4: Already-ran-today (D-08) - recommended: `scrape_runs` + `credit_usage`
Data already recorded: `scrape_runs(book_key, ran_at, status 'ok'|'failed', ...)` - one row per book per run, appended by `recordScrapeRun` (src/ingestion/promos/store.ts), `status` is "ok" or "failed" (src/ingestion/promos/run.ts). `credit_usage(recorded_at, triggered_by_user_id)` rows are written by `runOddsRefresh`; scheduled morning refresh uses `triggeredByUserId: null`, user-triggered refreshes carry a user id.
`promos.last_seen_at` is NOT suitable (updated per-promo; a run that finds nothing leaves it alone). `promo_profit_observations` is NOT suitable for the observe check (also written by every Promos-tab load via getPromos).

Rule (compute in app code with the existing `denverDate()` from `src/domain/promos/profitTotals.ts`, never SQL timezone math):
- `scrapedToday` = exists a `scrape_runs` row with `status='ok'` whose `denverDate(ran_at) === denverDate(now)`. Query: `select max(ran_at) from scrape_runs where status='ok'` -> compare dates. (One book "ok" counts; if the morning run partially failed - one book failed - the backup is skipped; acceptable per D-07 wording "a successful scrape happened". If owner prefers stricter, require every book in SCRAPE_TARGET_BOOK_KEYS ok - flag as open question.)
- `observedToday` = exists a `credit_usage` row with `triggered_by_user_id IS NULL` and `denverDate(recorded_at) === today`. Independent of the scrape check so a failed refresh is retried by the backup, and a successful observe is never repeated (no double credit spend).
- Script `scripts/already-ran-today.ts` (dotenv `.env.local` load like siblings) prints and appends `scrape_done=true|false` and `observe_done=true|false` to `$GITHUB_OUTPUT`. On any DB error, output both `false` (fail open = run the scrape; the observe step still self-limits via its Denver window).
- Workflow: step id `today`, then `if: github.event_name != 'schedule' || steps.today.outputs.scrape_done != 'true'` on the scrape step; observe step `if: ${{ !cancelled() && (github.event_name != 'schedule' || steps.today.outputs.observe_done != 'true') }}`. Skip applies only to the `schedule` event so manual and cron-dispatched runs always run. Needs `DATABASE_URL` env on the check step; it runs after `npm ci` (cost: ~30-60s of Actions minutes, negligible).
- Edge: GitHub schedule can fire late; at 15:37 UTC the Denver hour is 9 (MDT) / 8 (MST) so `isMorningObservationWindow` (<10) still passes unless delayed past 10:00 MDT - then the observe step no-ops, which is the safe outcome.
- Edge: if the Vercel cron is delayed to the end of its hour (13:59 UTC) and GitHub queues, there is no overlap with 15:37 UTC; the `concurrency: scrape-promos` group already serializes runs.

### Anti-Patterns to Avoid
- Running the scraper inside the Vercel function (D-01 forbids; also `tsx` scripts/DB writes belong on GitHub).
- Using `schedule` + `timezone:` key (already tried; silently never fired - see workflow comment).
- Passing `force_morning_observe` as boolean `true` JSON (use string "true").
- Logging the Authorization header, the token, or the full GitHub error body unbounded.
- Treating the cron request as authenticated by IP/User-Agent (`vercel-cron/1.0`); only the bearer secret counts.

## Common Pitfalls

### Pitfall 1: proxy.ts redirects the cron request to /login
**What goes wrong:** `src/proxy.ts` matcher covers every path except static assets; a no-cookie request to `/api/cron/scrape` is 307'd to `/login`. Vercel cron does not follow redirects, so nothing is dispatched and the log may not even show it ("redirect responses are not shown in logs").
**How to avoid:** Add `pathname.startsWith("/api/cron/")` to the pass-through condition (the route enforces its own bearer auth) and cover with a proxy unit test; or narrow the matcher with `api/cron`. Warning sign: Vercel cron "View Logs" empty, GitHub shows no dispatched run.

### Pitfall 2: Hobby cron timing/delivery assumptions
Fires any minute 13:00-13:59 UTC; best-effort; may deliver twice; no retry. Idempotency: duplicate dispatch is harmless-ish (workflow `concurrency` queues the second; second run's morning-observe would re-spend a refresh unless guarded). Mitigation option: the route (or workflow) also applies the observe_done check to dispatched runs - recommended low-cost variant: let the check script's `observe_done` also gate the observe step when the run is a *second* dispatch... simplest: keep as designed and accept the rare duplicate; `runOddsRefresh` has a lock + credit ledger and the owner can see it. Flag in Open Questions.

### Pitfall 3: Workflow must exist on `main` before dispatch
Dispatch targets `ref: main` using the workflow file on that ref. Push the workflow edit (and keep `workflow_dispatch` input) before the first cron. Also GitHub disables scheduled workflows in public repos after 60 days without repo activity (the backup `schedule`), irrelevant to dispatch.

### Pitfall 4: safeAction and redirect() from login/invite/logout
`safeAction.isFrameworkControlError` checks `digest.startsWith("NEXT_REDIRECT")` / `"NEXT_HTTP_ERROR_FALLBACK"` - matches Next's redirect digest format (`NEXT_REDIRECT;replace;/login;307;`) and is unit-tested (safeAction.test.ts). Next 16 docs recommend `unstable_rethrow` (marked unstable) for server-side try/catch; for client code the digest check is the safest stable approach. Keep it. Behavior caveat: for a server action that calls `redirect()`, Next's client handles the redirect itself; wrapping via safeAction must not swallow it - covered. Verify manually on the deployed site (login, invite redeem, logout still navigate).

### Pitfall 5: Neon driver on Vercel
`neon-http` is stateless per query: no pool exhaustion. The existing code uses `neon(url)` + lazy singleton; fine. Use the pooled or direct Neon connection string - HTTP driver works with either. Latency: place Vercel Functions region near the Neon region (Project Settings -> Functions -> Region; default iad1 = us-east; check Neon project region) [ASSUMED defaults; owner checks]. Multi-statement `db.batch` used by store is a Neon HTTP batch: unaffected.

### Pitfall 6: Env vars and build
Env vars must be set for Production (and Preview if previews are used) before the first meaningful request; changes require a redeploy. `SESSION_SECRET` >= 32 chars else getSessionOptions throws at login. `APP_URL` is only used by the local `invite:create` script - setting it in Vercel is harmless but the script reads `.env.local`; owner should update their local `.env.local` APP_URL to the deployed URL to get correct links (call this out).

### Pitfall 7: Preview deployments hit the live DB
Branch/preview deployments share the same env vars if scoped to Preview; recommend scoping all secrets to Production only (owner choice) so previews can't touch the live Neon DB. Cron only runs on production regardless.

### Pitfall 8: Failed GitHub token silently expires
Fine-grained PATs have a mandatory expiration (max 1 year by default org policy; can be set). When it expires the dispatch returns 401; the backup schedule then becomes the only run. Record expiry date in the human checkpoint and note it in README/STATE.

## Security Domain

### Applicable ASVS Categories
| Category | Applies | Control |
|----------|---------|---------|
| V2 Authentication | yes (cron endpoint) | Bearer CRON_SECRET, fail closed, timing-safe compare |
| V3 Session Mgmt | yes | iron-session `httpOnly`, `secure` in production, `sameSite: lax` (existing) |
| V4 Access Control | yes | proxy exemption limited to `/api/cron/`; route self-authenticates; server actions keep `requireUser()` |
| V5 Input Validation | low | Route takes no input; GET only |
| V6 Cryptography | yes | CRON_SECRET/SESSION_SECRET from `openssl rand`; never hand-rolled |
| V14 Config | yes | no secrets committed; no `NEXT_PUBLIC_`; token not logged |

### Known Threat Patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Anyone calling /api/cron/scrape to burn Actions minutes | DoS/Tampering | 401 w/o secret; unset secret = 401 |
| PAT leakage via logs/errors | Info disclosure | Log status codes only; token only in header; Actions-only repo-scoped PAT limits blast radius |
| PAT overscope | Elevation | Fine-grained, single repo, Actions rw only, expiry set |
| Preview deployments using prod DB | Tampering | Scope secrets to Production only |
| Invite links over http | Info disclosure | https only on Vercel; APP_URL https |
