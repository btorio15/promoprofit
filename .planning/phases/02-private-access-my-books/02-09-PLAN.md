<objective>
Close the owner-reported gap: "there is no way to get out of the settings screen and back to the main page." /settings DOES render AppHeader, but the header's "PromoProfit" wordmark is a plain span (02-UI-SPEC.md line 42 made it "plain text, not a link (there is no other page to navigate home to in this phase)" — a premise the Settings page itself invalidated), and the AccountMenu only offers Settings / Log out. So the only exit is the browser back button.

Chosen fix (most consistent with 02-UI-SPEC.md idioms), all three pieces:
1. AppHeader wordmark becomes a next/link Link to "/" — standard web convention, fixes every header-bearing page at once, no new visual element (same Heading 20px/600 text, no underline).
2. /settings gets an explicit "Back to PromoProfit" link above the "Settings" heading — muted Label-size text with a lucide ArrowLeft icon, min-h-10 tap target, following the existing plain-link idiom (invite page "Log in" link, D-18 "Manage your books" secondary link — never an accent button, since Save changes stays the one accent CTA per UI-SPEC Color rule 7). Discoverable for users who don't know the wordmark is clickable.
3. The save-success Alert reads "Your books were updated." followed by a "Back to PromoProfit" link, so a successful save leaves an obvious next step. No auto-redirect after save (UI-SPEC requires the inline confirmation to be visible).

02-UI-SPEC.md is amended to record the change (wordmark now a link; back-link copy added to the copywriting table).

/onboarding/books intentionally stays header-less with no back link: it is a gated one-time step (D-08, UI-SPEC "Book picker step"), and after plan 02-08 it can no longer loop — Continue is its exit.

Purpose: DASH-02 — settings is a usable, persistent screen the user can enter AND leave.
Output: header link, settings back link, success-alert link, render test, UI-SPEC amendment, owner check.
</objective>
