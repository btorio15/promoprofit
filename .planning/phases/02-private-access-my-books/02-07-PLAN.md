<objective>
Close verification gap 1 (CR-01, BLOCKER): the 5-attempt / 15-minute login lockout is bypassable by concurrent requests because login.ts reads lockedUntil, verifies the password, then recordFailedLogin does its own SELECT + UPDATE — three unsynchronized steps.

Fix per 02-REVIEW.md CR-01: reserve the attempt atomically in ONE conditional UPDATE ... RETURNING before argon2 runs; refuse (locked) when the reservation matches zero rows; clear on success. neon-http has no interactive transactions, so atomicity comes from a single statement: Postgres takes a row lock for the UPDATE and, under READ COMMITTED, re-evaluates the WHERE clause against the latest committed row version after a concurrent updater commits — so once one request writes locked_until, every queued request's WHERE fails and it returns zero rows.

Purpose: DASH-04 (only invited users can log in) relies on the lockout as its brute-force control (T-02-09).
Output: reserveLoginAttempt in accounts.ts, recordFailedLogin deleted, login.ts reordered, statement test + concurrency test.

Scope note: WR-02 (distinct "locked" outcome enables enumeration) and WR-03 (timing) are NOT included — the user-visible "locked" status and message stay exactly as today. No schema change (existing users.failed_login_attempts / users.locked_until columns are reused).
</objective>
