# Phase 3 — UI Design Contract

> Visual and interaction contract for Promo Scraping & Review. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Non-interactive research run:** `03-CONTEXT.md` already locks every scope, flow, and copy-tone decision for this phase (D-01…D-19), or explicitly hands the remainder to "Claude's Discretion": promo/scrape-run/alias table shape, the confidence-scoring *method* (its strictness is D-10's call, not this doc's), Promos-tab row layout and sorting, the boost-math implementation location, and scraper code layout. The design-system tokens (shadcn preset, palette, spacing, typography) are **unchanged from Phase 1/01.1/2** per the CONTEXT.md canonical-refs instruction — this phase adds one new tab and its states on top of the existing system, it does not introduce a new one. Items marked **"Claude's discretion — defaulted"** below are the presentation choices CONTEXT.md left open, resolved using the established finder/arb idiom (`ResultRow.tsx`, `ArbRow`/`ArbResultsList.tsx`, `OddsStatusBar.tsx`, `RiskAdvisory.tsx`, `RefreshConfirmDialog`) rather than inventing new patterns. No interactive channel was available in this session (CONTEXT.md left nothing design-relevant unanswered), consistent with how the 01.1 and 02 UI-SPECs were produced.

**Notable outcome:** unlike Phase 2 (added `dropdown-menu`) and Phase 01.1 (added `popover`, `checkbox`), **this phase adds zero new shadcn blocks.** Every primitive it needs — `select`, `alert-dialog`, `badge`, `collapsible`, `table`, `tooltip`, `card`, `input`, `button` — is already installed and already used for an analogous purpose elsewhere in the app.

## Layout & Responsive Behavior

(Not in the base template — added because this phase introduces a new top-level tab with two list surfaces — a review queue and an active-promos list — plus a per-book status readout, none of which existed in Phase 1/01.1/2.)

### Top-level tabs (D-01)

- `AppShell.tsx`'s `Tabs` gains a third `TabsTrigger`: **Bonus bets | Arbitrage | Promos**, in that order (D-01: "a third tab after Bonus bets | Arbitrage"). Same `TabsList variant="line"` component, same `keepMounted` `TabsContent` pattern (switching tabs never discards another tab's in-flight state) — no new tab component, `ActiveTab` type in `AppShell.tsx` extends to `"bonus" | "arbitrage" | "promos"`.
- The shared `OddsStatusBar` and `CreditBanner` stay exactly as-is, above the tabs — the Promos tab still depends on cached odds/credits for its hedge math (D-05 carries forward CALC-05's market rules), even though scraping itself spends no credits (D-07). **No new status-bar line is added for scraping** — the "Odds updated…" and "Spreads & totals updated…" lines are unaffected; per-book scrape freshness gets its own panel inside the Promos tab body instead (below), because it's promo data, not odds data, and conflating the two in one sticky bar would blur what's actually stale.

### Promos tab panel, top to bottom

1. **Panel header:** "Promos" (Heading, 20px) + one-line description (Label, muted), matching the finder/arb header pattern exactly.
2. **Scrape status panel** (D-08, new — no existing analog): an always-visible `Card`-like block (`rounded-lg border border-border bg-secondary p-4`), **not** a `Collapsible` — per-book freshness is exactly the kind of "is this trustworthy right now" context the app already surfaces unconditionally (odds age, credit meter), so it gets the same always-visible treatment rather than a click-to-reveal disclosure. One line per configured book, in book-list order (`COLORADO_BOOKS`):
   - Fresh: `{Book} promos updated {N}h ago` (Label, `text-muted-foreground`).
   - Failed last run (D-08): `{Book} promos updated {N}h ago · last run failed` (Label, `text-warning`, leading `TriangleAlert` icon `size-4` — identical visual treatment to `OddsStatusBar`'s stale-odds line) — **not destructive red**, because a failed run does not wipe or corrupt existing promos (D-08 says they "stay until they expire"); it's a freshness warning, not an error state the user must act on immediately.
   - Never scraped yet (first run hasn't completed for that book): `{Book} promos not scraped yet` (Label, `text-muted-foreground`).
3. **"Needs review (N)" section** (D-13) — rendered **only when N > 0**; the section (heading included) is entirely absent when the queue is empty, same "don't show an empty container" instinct as the rest of the app (Claude's discretion — defaulted: a permanently-visible "Needs review (0)" heading would be noise on every visit, and there's no action to take from an empty queue).
   - Section heading: **"Needs review ({N})"** (Heading, 20px), count in `.num`.
   - One-line description (Label, muted): "Scraped promos we couldn't confidently match. Confirm, correct, or dismiss each one before it's used in hedge math."
   - A vertical stack (`gap-3`) of **queue-item cards** — see "Queue item card" below. **Not** the Collapsible/expand-row pattern used elsewhere — this list is action-oriented (each item needs inline forms and three-way branching actions), not browse-and-compare, so a plain `Card` per item with inline state is the right divergence from the finder/arb row idiom, not an oversight.
4. **`RiskAdvisory`** (shared component, verbatim, CALC-06/D-05) — placed **directly above the active-promos list**, below the review-queue section, mirroring the finder/arb "advisory sits right before the rows it warns about" placement (the advisory is about placing exact stakes on live hedges, which describes the active-promos list, not the review queue).
5. **Active promos list** — see "Promo row" below. Sorted by **guaranteed profit, descending** (Claude's discretion — defaulted: fixed order, no user-facing sort control this phase — DASH-01 in Phase 4 is where "user can sort by profit and by ROI/conversion %" becomes an interactive requirement; building a sort UI here would pre-empt Phase 4's actual feed work). No sport sub-tabs this phase either (Claude's discretion — defaulted: arb's sport sub-tabs exist because arb volume across 5 sports is large; a freshly-scraped single-book promo list starts small, and Phase 4's opportunities feed is where cross-cutting filters belong).
6. **Empty states** — see "Empty states" below.

### Queue item card (D-13, D-14)

`Card`-equivalent (`rounded-lg border border-border bg-secondary p-4`, `flex flex-col gap-3`). Two **kinds**, both sharing this shell, distinguished by the parsed reason the promo needs review:

- **Match review** (D-10/D-11 — event/market confidence below the auto-accept threshold):
  1. Summary line (Body, 16px): `{Book} — {promo-type Badge} · {parsed description}` e.g. "DraftKings — **Boost** · 50% profit boost, moneyline, NFL."
  2. Reason line (Label, muted): "Needs review: couldn't confirm which game this is for."
  3. Best-guess line, shown only when a candidate exists (Label, muted): "Best guess: {away} @ {home}, {kickoff} — {market/side}." This is presentational only; it never auto-activates (Anti-Pattern 2 guard, D-10).
  4. Actions row (`flex flex-wrap gap-2`, each `h-10` / ≥40px tap target):
     - **Confirm** (`Button`, accent fill) — only rendered when a best-guess candidate exists; accepts it as-is.
     - **Correct** (`Button variant="outline"`) — toggles the correction sub-panel (below).
     - **Dismiss** (`Button variant="outline"`, `text-destructive`) — opens the shared dismiss `AlertDialog` (below).
  5. **Correct sub-panel** (revealed inline below the actions row, `rounded-lg border border-border bg-background p-4 mt-1`, ARCHITECTURE.md Pattern 1 "dropdown-first"):
     - **Event** `Select` — options grouped by sport (`SelectGroup`/`SelectLabel`, one group per in-season sport), each option formatted identically to a row's Game cell: "{away} @ {home} · {kickoff}", sourced from cached Odds API events (zero additional API cost — reads the existing cache, never fetches).
     - **Market / side** `Select` — disabled until an event is chosen; options depend on that event's cached markets: "Moneyline — {team}" (×2), "Spread {±X.5} — {team}" (×2, half-point only per CALC-05), "Total {O/U X.5}" (×2). Formatted with the same market-badge vocabulary as the arb tab (D-15 reuse: "Spread +3.5", "Total O/U 44.5").
     - **Save match** (`Button`, accent fill, disabled until both selects have a value) / **Cancel** (`Button variant="ghost"`) — Cancel collapses the sub-panel without discarding the queue item.
- **Cap review** (D-18 — event/market matched fine, but max-stake/max-winnings/min-odds text couldn't be parsed):
  1. Summary line (Body, 16px): same format as above, plus the confirmed game/market inline since that part is already known: "DraftKings — **Boost** · 50% profit boost, NFL moneyline, Broncos @ Chiefs."
  2. Reason line (Label, muted): "Needs review: couldn't read the stake/winnings cap from the promo text." Any field that *did* parse successfully is shown read-only (Label, muted) so the reviewer isn't re-entering everything: "Max stake: not found · Max winnings: $500 (parsed) · Min odds: not found."
  3. Actions row: **Enter cap details** (`Button variant="outline"`) toggles the cap sub-panel; **Dismiss** (`Button variant="outline"`, `text-destructive`) same dialog as above. No "Confirm" button for this kind — there is nothing to accept as-is; the whole point is a human-entered number (D-18: "the math never guesses a cap").
  4. **Cap sub-panel:** one `Input` per unparsed field only (Max stake / Max winnings / Min odds — money or American-odds formatted, same validation idiom as the finder's Bonus amount field), plus **Save & activate** (`Button`, accent fill, disabled until every shown field has a value) / **Cancel** (`Button variant="ghost"`).

**Dismiss confirmation** (shared `AlertDialog`, both kinds — reuses the exact `RefreshConfirmDialog`/`Search spreads & totals` confirm-dialog component, new copy only):
- Heading: "Dismiss this promo?"
- Body: "It won't be suggested again from later scrapes of this book. This can't be undone from here." (D-14)
- Buttons: **Dismiss** (destructive-styled confirm button) / **Cancel** (ghost).
- Claude's discretion — defaulted: this is the one meaningfully irreversible action in this phase (D-14: a dismissal is never re-queued), which is exactly the bar Phase 2's Color section set for reserving red/a confirm dialog — Confirm and Correct are not gated behind a dialog because both remain correctable later (D-11's flag-back safety net), but nothing undoes a Dismiss in this UI.

**Attribution (D-12, "Refreshed by" pattern reuse):** once a queue item is acted on, it leaves the queue entirely (no persistent queue history view this phase). The resulting **active** promo row carries the attribution instead, in its expanded panel only (not the collapsed row, to avoid clutter): "Confirmed by {displayName}" / "Corrected by {displayName}" / "Cap entered by {displayName}" — same muted Label styling and `·`-suffix convention as `OddsStatusBar`'s "Refreshed by {displayName}". Auto-matched promos (above the threshold, D-10) show no attribution line at all — there's no human to attribute.

### Promo row (active promos list)

Reuses the finder's `ResultRow.tsx` six-column grid **verbatim** (`grid-cols-[minmax(0,1.3fr)_minmax(0,1fr)_minmax(0,1.2fr)_120px_96px_20px]` desktop, stacked mobile), wrapped in the same `Collapsible` (whole row is the trigger, ≥44px mobile tap target) — this is the "compact expandable row pattern from finder/arb" the objective calls for, applied to a promo+hedge pairing rather than a bonus+hedge or side-A+side-B pairing:

- **Col 1 — Game:** `{sport} · {kickoff}` caption (unchanged pattern), **market badge** (D-15 reuse: "Moneyline" / "Spread ±X.5" / "Total O/U X.5") inline after the caption, then **"Auto-matched" badge** (D-11, `Badge variant="outline"`, only on promos that cleared the threshold automatically — never on human-confirmed ones) plus a **flag-back icon button** (`Button variant="ghost" size="icon"`, `Flag` lucide icon `size-4`) immediately after it, `onClick` calls `e.stopPropagation()` before dispatching (same technique 01.1's `MultipleBooksPopover` trigger already uses inside a `CollapsibleTrigger`, so tapping the flag never also toggles the row). Below the caption line, the **fine-print note** (D-17, Label, muted, `line-clamp-1`): any parsed non-structured term such as "Opt-in required" or "New customers only" — if truncated, the full text is reachable via the same static-text `Tooltip` pattern as "Tie risk" (hover on desktop, tap on mobile since it's short one-line prose, not a list).
- **Col 2 — Promo:** promo-type `Badge variant="outline"` ("Boost" or "Bonus bet") next to the book name, then the promoted side + price: the **boosted price when the book published one** (D-03 — "the math uses it, because books round their own boosted odds"), otherwise the app's own computed boosted price from boost % + current odds, formatted identically to any other odds figure (`.num`, American odds).
- **Col 3 — Hedge:** unchanged finder pattern — team + odds (`.num`) + hedge book name below, **"Same book" badge** (D-04, `Badge variant="outline"`, reused verbatim) when the best hedge happens to be at the same book that offered the promo, **"Tie risk" badge** (reused verbatim, unchanged tooltip) when applicable.
- **Col 4 — Guaranteed profit:** `.num text-xl font-semibold text-primary`, unchanged treatment.
- **Col 5 — ROI / Conversion:** label is **dynamic per row's promo type** (Claude's discretion — defaulted, mirrors the finder's dynamic mobile column labels): boosts show `{formatPct(roiPct)}` captioned "ROI"; bonus-bet promos show `{formatPct(conversionPct)}` captioned "Conversion" — same visual slot, same typography as the finder's Conversion column.
- **Col 6 — chevron:** unchanged.
- **Expanded panel:** reuses `ResultDetails.tsx`'s exact two-column layout (Display-size profit restatement, numbered A/B steps, per-outcome payout table) with two additions: (1) the cap note, when the promo's max-stake or max-winnings cap actually bound the stake choice (D-02/CALC-03) — a Label-size line under the profit restatement: "Capped at {book}'s {$X} max stake — a smaller stake keeps guaranteed profit equal on both sides." (2) the attribution line described above, when present.

### Empty states

Four distinct empty states on this tab, each reusing the existing `EmptyState`/`ArbEmptyState` visual shell (`rounded-lg border border-dashed border-border bg-background p-6`, Heading + Body + optional CTA):

1. **No promos scraped yet at all** (first-ever run hasn't completed for any book): heading **"No promos scraped yet"**, body: "The scheduled scraper hasn't completed a run yet. Check back after the next scheduled run, or ask the person who set this up to trigger one." No CTA — there is no manual-add path in this phase (that's Phase 5).
2. **No active promos right now** (scraper has run, nothing currently qualifies — e.g. all expired): heading **"No active promos right now"**, body: "None of the scraped promos currently qualify for a hedge. New ones appear automatically after the next scheduled scrape."
3. **No promos at your books right now** (promos exist, but none are hedgeable at the user's selected books — reuses the Phase 2 D-18 pattern verbatim, extended to this tab): heading **"No promos at your books right now"**, body: "None of the currently active promos are hedgeable at the sportsbooks you've selected. Add more books to see more opportunities." + `Button variant="outline"` render `Link` to `/settings`: **"Manage your books"**.
4. **No cached odds yet** (promos exist but hedge math needs odds that haven't been fetched — reuses the finder/arb's verbatim empty state): heading **"No odds cached yet"**, body: "Press Refresh odds to pull current Colorado odds before these promos can show a hedge."

Unchanged: all new inputs/buttons/selects ≥40px height (`h-10`), the flag icon-button and every queue-item action button ≥40px, full mobile promo-row tap target ≥44px (same fixed exception as Phase 1/01.1). Dark mode: unchanged, OS `prefers-color-scheme` only.

**Accent reserved for (exhaustive — extends 02's list with items 8 and 9; nothing else may use accent):**
1. "Find hedges" primary CTA fill (unchanged)
2. The guaranteed-profit dollar figure in every result row on **all three tabs**, collapsed and expanded (unchanged, extended to Promos rows)
3. The active/selected chip in any single-select toggle group (unchanged)
4. The checked-state fill of any checkbox (unchanged)
5. Input focus ring (`focus-visible`) on all form controls, every screen (unchanged, extended to the new Selects/Inputs in correction sub-panels)

7. The single primary CTA fill per new auth/settings screen (unchanged, Phase 2)
8. **(new)** The **Confirm** button in a match-review queue card, and the **Save match** / **Save & activate** buttons inside a correction sub-panel — each is the moment an uncertain promo becomes a trusted, active one, the same semantic family as item 7
9. **(new)** Input focus ring aside, no other element in the review queue is accent — see below for what's explicitly excluded

**Destructive reserved for (exhaustive — new list this phase; the first phase with an actual destructive action):**
1. Inline field validation errors (unchanged, all forms)
2. Refresh/search blocked and failure alerts (unchanged, `OddsStatusBar`/arb)
3. **(new)** The **Dismiss** button's text/icon in a queue-item card (`variant="outline"`, `text-destructive` — outline, not filled, since the click itself doesn't destroy anything; the dialog is where the irreversible step happens)
4. **(new)** The **Dismiss** confirm button inside the dismiss `AlertDialog` — the one truly irreversible action in this phase (D-14)

**Explicitly NOT accent or destructive (Claude's discretion — defaulted):**
- **Correct** and **Enter cap details** are `variant="outline"` — they open a form, they don't commit anything by themselves; only the form's own Save button (accent) or Cancel (ghost) commits or discards.
- The **flag-back** icon button is `variant="ghost"`, no accent, no destructive tint — flagging is a low-stakes, fully reversible safety action (the promo simply re-enters the review queue; nothing is lost), the same reasoning Phase 2 used to keep "Log out" un-red.
- The per-book "last run failed" scrape-status line is **warning (amber), not destructive** — existing promos aren't wiped by a failed run (D-08), so it's a freshness caveat, not an error demanding action.
- The "Auto-matched" and market/promo-type/Same-book/Tie-risk badges all stay `Badge variant="outline"` (neutral), unchanged from the existing badge idiom — none of them are accent, consistent with 01.1's "Multiple books" badge precedent.
