# Phase 01.1: Code Review Report

**Reviewed:** 2026-09-26T02:34:09Z
**Depth:** standard

## Narrative Findings (AI reviewer)

## Summary

I reviewed the Arbitrage tab phase: the arb stake solver and ranking, the spreads/totals extractor, the extended refresh orchestration and cache queries, the arb UI, and the finder's "Limit hedge amount" change.

The decimal.js discipline holds. I found no native-float money math, and the half-point / signed-home-point grouping in `spreadsTotalsFilter.ts` is correct. The different-book constraint and the strict `impliedSum < 1` check in `rankArbs.ts` / `arbMath.ts` are also correct.

Two problems produce wrong results:

1. **The whole-dollar arb solver is not optimal.** It returns less profit than is possible, and sometimes reports "no arb" when a real arb exists.
2. **The finder's hedge-amount cap is applied after the best orientation per game is chosen.** This throws away games where the other orientation fits under the cap.

**Focus item 1 (partial-refresh visibility): the problem is real.** `refresh.ts` behaves the same way and has since Phase 1 (by design, WR-01). I classify it as a WARNING, not a BLOCKER. No wrong money is ever shown: the failure hides data rather than serving stale data. It also recovers on the next successful refresh. The new part is the wider impact: a failed *opt-in* spreads search can now shrink the Bonus-bets tab. Details are in WR-01.

**Focus item 4 (credit gate): the gate holds.** Every credit spend is gated server-side on `confirmed: true`, and only the dialog sends that. There are two gaps: the dialog's Cancel button is not disabled mid-request (WR-04), and no auth exists yet (WR-05, deferred to Phase 2). The race guard also misses the invalid-input case (WR-02).

## Critical Issues

### CR-01: Whole-dollar arb solver misses the optimal stake split and hides real arbs

**File:** `src/domain/hedge/arbMath.ts:89-136`
**Issue:** `calculateArb` only considers the floor/ceil of the *full-total* proportional split: four candidates, all of which lay close to `totalStake`. D-01 makes the total stake a **cap**, not a target. The best allocation often lays noticeably less than the cap, because a smaller whole-dollar pair can land much closer to the balanced ratio.

I checked this by brute force: exhaustive whole-dollar search over every `(stakeA, stakeB)` with `stakeA + stakeB <= T`, using the same cent-floored payouts. It was run as a temporary vitest file that I then deleted. There were 78 mismatches across 16 odds values × 6 stakes. Examples:

| Odds A / B | Total | Solver result | Achievable |
|---|---|---|---|
| -150 / +200 | $10 | `null` (no arb shown) | $0.33 at 5/3 |
| -250 / +400 | $7 | `null` | $0.20 at 3/1 |
| -250 / +300 | $25 | $0.20 at 18/7 | $0.80 at 17/6 |
| -300 / +400 | $50 | $2.00 at 39/11 | $2.33 at 37/10 |

Whole-dollar is the **default** precision. So by default the tab both hides real arbs and under-reports guaranteed profit and return %. That also skews the ranking, which sorts by `returnPct`. This breaks the project's core value: every opportunity, correct to the cent.

**Fix:** Search the whole grid of stake-A values up to the cap. For each one, pick the stake-B values that best balance it:
```ts
const unit = dp === 0 ? new LocalDecimal(1) : new LocalDecimal("0.01");
const ratio = oddsA.dividedBy(oddsB); // stakeB ≈ stakeA * Da / Db balances payouts
for (let stakeA = unit; stakeA.lt(totalStake); stakeA = stakeA.plus(unit)) {
  const balancedB = clean(stakeA.times(ratio));
  for (const stakeB of roundingCandidates(balancedB, dp)) {
    if (stakeB.lte(0) || stakeA.plus(stakeB).gt(totalStake)) continue;
    // ...same payout/profit/tie-break evaluation as today
  }
}
```
For cents precision, the full grid can reach 10M steps at the $100k cap. Bound it by walking `stakeA` down from the proportional split for a fixed window, for example a few thousand units. Alternatively, iterate total-laid values from the cap downward and stop once `L * (1/impliedSum - 1)` falls below the best profit found so far; that is a valid upper bound. Add a table-driven test that checks against brute force for small totals, like the cases above.

### CR-02: Finder hedge cap drops games whose other orientation fits under the limit

**File:** `src/domain/hedge/rankBonusBetHedges.ts:115-137` (cap added in this phase at 131-137); `src/app/actions/find-hedges.ts:134-148`
**Issue:** For each market, `rankBonusBetHedges` keeps a single `best` orientation (highest profit), and only then filters by `maxHedgeStake`. The highest-profit orientation is typically the bonus on the longshot, which needs the *largest* hedge stake. The favorite-side orientation needs a much smaller hedge and still has positive profit, but it has already been discarded before the cap runs.

So a capped user loses exactly the games the cap was meant to surface. `limitExcludedAll` then shows "No hedges fit under your limit — every result needs a hedge stake above your $X limit" (`EmptyState.tsx`), which is false when a qualifying orientation exists. D-18's own reasoning ("apply the cap BEFORE sort/slice") applies equally to the per-event reduction.

**Fix:** Apply the cap inside the per-market loop, before choosing `best`:
```ts
for (const bonusQuote of bonusQuotes) {
  const opportunity = buildOrientation(market, bonusQuote, opts);
  if (!opportunity) continue;
  if (opts.maxHedgeStake !== undefined && opportunity.result.hedgeStake.gt(opts.maxHedgeStake)) continue;
  if (!best || opportunity.result.guaranteedProfit.gt(best.result.guaranteedProfit)) best = opportunity;
}
```
Then remove the post-loop `withinCap` filter. Add a test where the higher-profit orientation exceeds the cap and the other orientation fits.

## Warnings

### WR-01: A mid-loop refresh failure hides every sport not yet refreshed until the next full refresh (focus item 1: the issue is real)

**File:** `src/ingestion/odds/refreshExtended.ts:186-213`, `src/db/queries.ts:52-80, 108-136`; the same pattern exists in `src/ingestion/odds/refresh.ts` (runGuardedRefresh loop, not in this diff)
**Issue:** This is how the failure plays out:

1. The loop writes each sport to `cached_extended_odds` **and** `cached_odds` with the new `now` as soon as that sport's fetch returns.
2. Suppose sport 2 of 5 throws. Sport 1's rows now carry `fetched_at = T1`, and sports 2–5 still carry the previous batch's `T0`.
3. `getCachedEvents` / `getCachedExtendedEvents` filter to `fetched_at = max(fetched_at)`, so they return **only sport 1**.
4. Sports 2–5 disappear from the Arbitrage tab *and the Bonus-bets finder*. The finder is new collateral: a failed spreads search now shrinks it, which was impossible before this phase.
5. The UI gives no hint. `handleSearchOutcome` shows "the Odds API didn't respond" and does not `router.refresh()` on error, so the status bar keeps the old age and a stale credit meter even though credits were spent and recorded.

There is also a sub-case: `replaceExtendedSportOdds` succeeds but `replaceSportOdds` (line 203) throws. The two caches then diverge, and only the extended cache hides its other sports.

`refresh.ts` has the identical behavior. It is documented as intentional (WR-01 in the Phase 1 review) and is exercised by `refreshExtended.test.ts:282` ("no purge runs"). The failure hides data and recovers, and no incorrect money is shown, so this is a WARNING rather than a BLOCKER. Still, recovering requires another paid refresh, and `schema.ts:40-50` claims D-16 isolation ("this table never touches cached_odds ... correct by construction"), which this path breaks.

**Fix:** Buffer, then commit once. Fetch every sport into memory, recording quota after each fetch exactly as today. Only after the loop completes, write all sports for both tables plus the purges in a single `db.batch([...])`, so a partial run changes nothing. Apply the same change to `refresh.ts`. Also call `router.refresh()` in `ArbForm.handleSearchOutcome` for `error`/`busy` outcomes so the credit meter reflects the spend. If rows must be written incrementally, add a `refresh_batch` table and filter reads on the last *completed* batch id instead of `max(fetched_at)`.

### WR-02: ArbForm keeps showing stale results for a stake the user has since changed or invalidated, and can show the skeleton forever

**File:** `src/components/arb/ArbForm.tsx:74-100, 263-268`
**Issue:**
- (a) `requestIdRef` only increments when a request is *sent*. If the user edits the stake to something invalid (such as clearing the field), no request is sent. Any in-flight request for the previous stake then passes the `requestId === requestIdRef.current` check and overwrites `response`. The list keeps rendering stakes for the old total next to a field error.
- (b) A server `invalid` result sets the error but leaves the previous `response` in place.
- (c) If the persisted `promoprofit.arb.totalStake` value is invalid on mount (for example `""` or `"abc"` left in localStorage), no request ever fires. `response === null && hasCachedOdds` then renders skeletons indefinitely.

**Fix:** Bump `requestIdRef.current` (and `setResponse(null)`) in the effect whenever validation fails. Clear `response` on an `invalid` result. Change the skeleton condition to `(response === null && hasCachedOdds && validation.success)`.

### WR-03: Credit estimates in the status are wrong after an extended search or a partial run

**File:** `src/ingestion/odds/status.ts:52-55, 62-65`
**Issue:**
- `estimatedRefreshCredits` is taken as `latest.refreshCost` whenever that is greater than 0. After a spreads/totals search, the latest `credit_usage` row is the 3× extended cost, so `CreditBanner` quotes roughly 3× the real cost of a normal refresh.
- In the other direction, `estimatedExtendedRefreshCredits` uses `latest.sportsFetched`. After a partial run (for example 1 sport fetched), that is far lower than the real in-season count. `ArbForm.searchDisabled` (line 159-162) and the inline "about N credits" copy then under-state the cost, so the button stays enabled when it should be disabled.

The server gate still uses the correct count, so no credits are overspent. What the user sees, though, is wrong.

**Fix:** Record the market count, or a `kind: "h2h" | "extended"` column, on `credit_usage`. Derive each estimate from the most recent *complete* row of its own kind, or always use the formula with a stored in-season sport count, never a partial run's `sportsFetched`.

### WR-04: The dialog's Cancel stays live while a confirmed (credit-spending) search is running

**File:** `src/components/arb/SearchSpreadsTotalsDialog.tsx:75-77`
**Issue:** `onOpenChange` correctly ignores close requests while `isPending`. However, `<AlertDialogCancel onClick={onCancel}>` calls `onCancel` directly and is not disabled. Clicking Cancel mid-request:

- closes the dialog, while the server action keeps running and spends credits;
- re-enables the main "Search spreads & totals" button, because `searchPending` belongs to ArbForm's transition, not the dialog's.

The user believes they cancelled a spend that still happens, and can start a second request, which will just get "busy".

**Fix:** Add `disabled={isPending}` to `AlertDialogCancel` and guard `onClick={() => { if (!isPending) onCancel(); }}`. Consider lifting the pending state into ArbForm so `searchDisabled` covers the confirmed request too.

### WR-05: The credit-spending server action has no authorization, and the confirm step is purely client-side

**File:** `src/app/actions/refresh-spreads-totals.ts:15-28`
**Issue:** Any visitor who can reach the deployment can call `refreshSpreadsTotals({ confirmed: true })` directly and skip the dialog. Each call burns about 3× a normal refresh against the shared 500-credit month; only the 20-credit floor and the lock limit it. Auth is scheduled for Phase 2, and `refreshOdds` has the same exposure. This phase triples the cost per abusive call.

**Fix:** Until Phase 2 ships, gate both refresh actions behind a shared secret or deployment protection (for example Vercel password protection, or an env-configured token checked in the action). Otherwise, don't deploy publicly.

### WR-06: Interactive popover and tooltip triggers are nested inside the row's Collapsible trigger button

**File:** `src/components/arb/MultipleBooksPopover.tsx:21-31`, `src/components/arb/ArbRow.tsx:27, 36-48, 58-72`
**Issue:** `CollapsibleTrigger` renders a `<button>`. The "Multiple books" `PopoverTrigger` and the "Tie risk" `TooltipTrigger` render focusable, interactive elements inside it. Interactive content nested inside a `<button>` is invalid HTML and is announced poorly by screen readers. `stopPropagation` only covers `click`: keyboard activation (Space/Enter keyup on the focused badge) can still reach the outer button and toggle the row. On mobile, the tap target for "Multiple books" lives inside the row's tap target.

**Fix:** Move the badges out of `CollapsibleTrigger`, for example into a sibling row element with the trigger covering only the text or chevron area. Alternatively, render the row trigger as a non-button element with its own `role="button"` handling and keep the badges outside its interactive subtree.

## Info

### IN-01: `worstCase` is almost always true in cents mode, contrary to its documented meaning
**File:** `src/app/actions/find-arbs.ts:65`, `src/domain/arb/types.ts:38`
**Issue:** The comment says the flag is "true only when whole-dollar rounding produced unequal outcomes". Cents mode floors payouts too, so the two nets usually differ by 1¢, and the details panel shows "(worst case)" on nearly every cents row.
**Fix:** Either update the doc and UI copy, or only set the flag when the nets differ by more than $0.01, or only in whole mode.

### IN-02: Pair selection uses default-precision Decimal while the stake solver uses a precision-40 clone plus `clean()`
**File:** `src/domain/hedge/rankArbs.ts:63-65`
**Issue:** `new Decimal(1).dividedBy(...)` uses the global precision of 20. Mathematically equal implied sums from different price pairs can compare unequal on rounding noise, which bypasses the lexicographic tie-break. `calculateArb` re-checks the implied sum, so this is harmless today but inconsistent.
**Fix:** Reuse a shared `LocalDecimal` and `clean()` (export them from `arbMath.ts`) when computing `impliedSum` in `findBestArbPair`.

### IN-03: The 5-minute refresh lock can expire while a fetch hangs, since there is no request timeout
**File:** `src/ingestion/odds/client.ts:64`, `src/ingestion/odds/refresh.ts:30`
**Issue:** `fetch(url, { cache: "no-store" })` has no `AbortSignal.timeout`. A stalled 3-market request can outlive `REFRESH_LOCK_TTL_MS`, allowing a second refresh to take the lock and interleave writes and purges.
**Fix:** Add `signal: AbortSignal.timeout(30_000)`, and keep the total request budget per run below the lock TTL.

### IN-04: `odds:smoke --extended` spends credits without recording them in `credit_usage`
**File:** `scripts/odds-smoke.ts:49-99`
**Issue:** Each run spends 3 credits that the in-app meter never sees. The meter then drifts optimistic until the next in-app refresh reads the headers.
**Fix:** Call `recordCreditUsage` with the returned quota, or print a clear warning that the meter will be stale.

### IN-05: The `schema.ts` D-16 comment contradicts actual behavior
**File:** `src/db/schema.ts:40-50`
**Issue:** It claims the extended cache "never touches cached_odds". `refreshExtended.ts:203` writes `cached_odds` on every extended run. That misleads future maintainers about the WR-01 invariants.
**Fix:** Update the comment to describe the h2h projection and its purge coupling.

### IN-06: Hard-coded values that duplicate existing constants
**File:** `src/components/arb/SearchSpreadsTotalsDialog.tsx:54`, `src/components/arb/ArbForm.tsx:54`
**Issue:** `"of 500 credits"` ignores `status.total` and `FREE_TIER_MONTHLY_CREDITS`. The literal `"200.00"` duplicates `DEFAULT_TOTAL_STAKE`, which is otherwise only used by a test.
**Fix:** Pass the total through props and import `DEFAULT_TOTAL_STAKE`.

### IN-07: Finder recompute after a refresh reuses the stale cap payload
**File:** `src/components/finder/FinderForm.tsx:116, ~126-140`
**Issue:** `lastValidValues` stores the cap that was in effect at submit time. If the user unchecks "Limit hedge amount" and then refreshes odds, the automatic recompute still applies the old cap.
**Fix:** Rebuild the payload from the current checkbox and amount state when recomputing, or clear `lastValidValues.maxHedgeAmount` when the checkbox is toggled off.

### IN-08: Large copy-paste duplication between the refresh paths and the cache helpers
**File:** `src/ingestion/odds/refreshExtended.ts:96-252` vs `refresh.ts`; `src/db/queries.ts:30-136`; `src/ingestion/odds/store.ts:29-113`
**Issue:** The lock, gate and credit-recording logic and the latest-batch query/replace/purge helpers are duplicated per table. The WR-01 fix, and any future CR-01-style credit fix, now has to be applied twice and kept in sync.
**Fix:** Extract a shared `runGuardedFetch({ markets, writers })` and table-parameterized cache helpers.
