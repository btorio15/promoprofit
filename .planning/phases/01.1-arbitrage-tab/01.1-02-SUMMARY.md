# Phase 01.1 Plan 02: Extended Odds Cache Summary

**New `cached_extended_odds` Postgres table with its own writer/purge/latest-batch-read lifecycle, migrated onto the live Neon DB, while `cached_odds`'s WR-01 read/write contract stays byte-for-byte unchanged.**

## Performance

- **Duration:** ~12 min
- **Tasks:** 3 completed (2 code tasks + 1 blocking live-DB migration)
- **Files modified:** 7

## Accomplishments
- `cachedExtendedOdds` (src/db/schema.ts) is a structural twin of `cachedOdds` — same five columns, same two index shapes, named `cached_extended_odds` — with a doc comment marking it as D-16's independent spreads/totals cache, written only by the future "Search spreads & totals" refresh and never purged by a normal h2h refresh. `npm run db:generate` produced `drizzle/0002_flaky_hammerhead.sql`, containing only a `CREATE TABLE` and two `CREATE INDEX` statements for the new table — zero `ALTER`/`DROP` statements touch `cached_odds` (verified via grep gate).
- `src/ingestion/odds/store.ts` gained three sibling functions — `replaceExtendedSportOdds`, `purgeStartedExtendedEvents`, `purgeUnrefreshedExtendedEvents` — each a literal structural copy of its `cached_odds` counterpart, retargeted at `cachedExtendedOdds`. The existing `replaceSportOdds`/`purge*`/credit/lock function bodies are untouched; a `git diff -U0` gate (only import/header-comment removals allowed, count 0) mechanically confirms this.
- `src/db/queries.ts` gained `getCachedExtendedEvents()` and `getExtendedOddsFreshness()`, copying the WR-01 latest-batch pattern (`fetched_at = max(fetched_at)` scoped to the new table only) and the same Zod-validate-and-drop-with-console.warn behavior, returning `{ events: [], fetchedAt: null }` when the table is empty so the UI can render "not fetched yet" instead of an epoch date. `getCachedEvents`/`getOddsFreshness`/`getMaxFetchedAt` bodies are unchanged.
- `scripts/db-check.ts` now prints a second line, "Cached spreads/totals events (commence_time in future): N, fetched_at: ISO|none (table empty)", which fails loudly (relation-does-not-exist error) if the migration wasn't applied — this is what proved the live-DB migration succeeded.
- **[BLOCKING] Task 3** ran `npm run db:migrate` against the live Neon DB (drizzle-kit migrate, never push) — applied cleanly — then `npm run db:check`, which printed "Cached spreads/totals events (commence_time in future): 0, fetched_at: none (table empty)" alongside the pre-existing "Cached events (commence_time in future): 95" line, confirming both tables now coexist correctly in production.

## Decisions Made
- Declined to build a shared, table-parameterized purge/writer helper even though the extended functions are near-identical to the originals — the plan explicitly calls this out as a D-16 pitfall (a shared helper risks accidentally coupling the two tables' purge lifecycles). Literal duplication was chosen deliberately for isolation.
