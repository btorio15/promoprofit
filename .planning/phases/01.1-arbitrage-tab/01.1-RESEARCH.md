# Phase 01.1: Arbitrage Tab (INSERTED) - Research

**Researched:** 2026-09-25
**Domain:** Cross-book sure-bet arbitrage detection over already-cached (and newly opt-in-cached) Odds API data, reusing Phase 1's hedge-math/quota/cache infrastructure
**Confidence:** HIGH

## Summary

This phase adds no new external dependency and no new vendor integration — it is entirely a matter of **generalizing four Phase 1 modules** (`marketFilter.ts`, the ranking layer, `quota.ts`'s credit estimator, and the `cached_odds` cache) from "one fixed side (the user's bonus book) vs. best-of-the-rest" to "best-of-all-books vs. best-of-all-other-books," and from "h2h only" to "h2h, plus opt-in spreads/totals with a distinct fetch cadence and its own cache lifetime." Every piece of hard infrastructure (decimal.js precision-40 odds conversion, the cent-rounding-candidate pattern, the credit gate, the refresh lock, the latest-batch cache-freshness filter, the shadcn component set) already exists and is proven in production code from Phase 1. The two genuinely new pieces of domain logic are: (1) an **arb-pairing algorithm** that must search book-pairs rather than pick each side's independent best (because, unlike the finder where the bonus book is fixed by user input, both sides of an arb are themselves derived from "best price" — the two searches can collide on the same book, which D-06 forbids); and (2) a **half-point exact-line matcher** for spreads/totals, keyed by point value rather than just market key.

The single highest-risk design decision in this phase is **cache architecture**: the existing `cached_odds` table has `eventId` as its sole primary key and one global "latest batch" freshness filter (`getCachedEvents`/`getOddsFreshness`, keyed off `max(fetched_at)` across the *whole* table). D-16 requires spreads/totals to persist on their own age/lifecycle, independent of the normal h2h-only refresh, and CONTEXT.md explicitly says any new fetch path "must not break the finder's WR-01 latest-batch filter." Adding spreads/totals data to the *same* table (even with a new `market_group` column) would require changing the primary key to a composite and would put the finder's untouched, currently-passing `getCachedEvents` query at risk of subtle breakage the moment someone edits it carelessly. This research recommends a **separate table** (`cachedExtendedOdds`) instead — see Architecture Patterns — which requires zero changes to any Phase 1 file that reads `cached_odds`, and makes the "must not break WR-01" requirement trivially true by construction rather than by careful testing.

**Primary recommendation:** Keep moneyline arbs entirely inside the existing `cached_odds`/`getCachedEvents` path (extend `extractTwoWayMoneylines`'s sibling ranking layer, don't touch its cache read), add a **new, parallel** `cachedExtendedOdds` table + store/query functions for the opt-in spreads/totals fetch, and implement arb-pairing as an explicit book-pair search (not two independent "best price" lookups) so the D-06 different-books rule is enforced correctly even when the naive best price for both sides would otherwise be the same book.

### Pattern 1: Arb-pairing must be a book-pair search, not two independent "best price" lookups

**What:** For each candidate market (a moneyline event, or a specific spread/total line within an event), collect every `(bookKey, price)` quote for side A and every `(bookKey, price)` quote for side B. Evaluate **every (bookA, bookB) pair where bookA ≠ bookB** and pick the pair that minimizes `1/decimal(priceA) + 1/decimal(priceB)` (equivalently, maximizes return %). This is different from `rankBonusBetHedges.ts`'s `bestHedgeQuote`, which is safe there only because the bonus book is fixed by the user's own input (no collision is possible). Here, both sides come from "best price across all books," so the unconstrained best-of-each can land on the same book — which D-06 explicitly forbids — and simply demoting one side to its second-best is not guaranteed to be the best remaining cross-book pair (a different combination might beat it). With at most 7 books, this is a trivial O(n²) search (≤49 pairs) per market/line — no performance concern.
**When to use:** Every arb row (moneyline, spread, and total).
**Example:**
```typescript
// Source: derived from The Odds API's standard 2-way arb formula, decimal.js-typed to match this
// project's precision-40 americanOdds.ts convention
import Decimal from "decimal.js";
import { americanToDecimal } from "./americanOdds";

export interface SideQuote { bookKey: string; oddsAmerican: number }

export interface BestArbPair {
  sideA: SideQuote;
  sideB: SideQuote;
  impliedSum: Decimal; // < 1 means a true arb
  tiedBooksA: string[]; // other books exactly matching sideA's price (D-07 "Multiple books")
  tiedBooksB: string[];
}

export function findBestArbPair(
  sideAQuotes: SideQuote[],
  sideBQuotes: SideQuote[],
): BestArbPair | null {
  let best: BestArbPair | null = null;

  for (const a of sideAQuotes) {
    for (const b of sideBQuotes) {
      if (a.bookKey === b.bookKey) continue; // D-06: different books required
      const impliedSum = new Decimal(1)
        .dividedBy(americanToDecimal(a.oddsAmerican))
        .plus(new Decimal(1).dividedBy(americanToDecimal(b.oddsAmerican)));

      if (best === null || impliedSum.lt(best.impliedSum)) {
        best = { sideA: a, sideB: b, impliedSum, tiedBooksA: [], tiedBooksB: [] };
      }
    }
  }

  if (best === null) return null;

  // D-07 "Multiple books": exact American-odds ties, any book other than the chosen one.
  best.tiedBooksA = sideAQuotes
    .filter((q) => q.bookKey !== best!.sideA.bookKey && q.oddsAmerican === best!.sideA.oddsAmerican)
    .map((q) => q.bookKey);
  best.tiedBooksB = sideBQuotes
    .filter((q) => q.bookKey !== best!.sideB.bookKey && q.oddsAmerican === best!.sideB.oddsAmerican)
    .map((q) => q.bookKey);

  return best;
}
```
D-04/D-05 ("every true arb above 0%, no near-arbs") is then just `impliedSum.lt(1)` — no epsilon, no minimum-return threshold.

### Pattern 2: Extended (h2h+spreads+totals) fetch shares the gate/lock, not the cache

**What:** `refreshSpreadsTotals` (new server action → `runSpreadsTotalsRefresh` in a new `refreshExtended.ts`) reuses `tryAcquireRefreshLock`/`releaseRefreshLock` (the same `refresh_lock` row id=1), `getLatestCreditUsage`/`recordCreditUsage` (the same `credit_usage` table — there is only one Odds API credit pool, so both fetch paths must read/write the same balance), and `evaluateRefreshGate` (unchanged signature) — but writes to the **new** `cachedExtendedOdds` table via new `store.ts` functions, never touching `cached_odds`.
**When to use:** The "Search spreads & totals" button's server action only.
**Credit math:** `estimateRefreshCredits(inSeasonSportCount, bookmakerCount, marketCount)` with `marketCount=3` (h2h+spreads+totals). With today's 7 free-tier books (1 region-group) and ~4 in-season sports, that's `4 × 1 × 3 = 12` credits — versus the normal refresh's `4 × 1 × 1 = 4` credits, i.e. exactly 3× (D-14), verified against the official cost formula `cost = markets × regions` [CITED: the-odds-api.com/liveapi/guides/v4/, re-confirmed 2026-09-25 via WebFetch — "Every group of 10 bookmakers is the equivalent of 1 region... cost = [number of markets] x [number of regions]"].
**Client fetch change:** `fetchSportOdds` in `client.ts` needs an optional `markets: string[]` parameter (default `["h2h"]` to preserve the existing `refreshOdds` call site untouched); the extended refresh calls it with `markets: ["h2h", "spreads", "totals"]`.

### Pattern 3: Independent freshness/purge lifecycle per cache (D-16)

**What:** `cachedExtendedOdds` gets its own `replaceExtendedSportOdds`, `purgeStartedExtendedEvents`, and `purgeUnrefreshedExtendedEvents` — structurally identical to the existing `store.ts` functions but operating on the new table. Critically, **do not** reuse the existing `purgeUnrefreshedEvents(refreshFetchedAt)` function against the new table's timestamp inside the *normal* `runOddsRefresh` path, and do not call the extended-table purge functions from the normal refresh at all — this is what makes "a normal refresh does not clear them" (D-16) hold. The extended refresh purges only its own table, scoped to its own run.
**When to use:** `runSpreadsTotalsRefresh` only.
**Freshness for the UI:** add `getExtendedOddsFreshness()` (parallel to `getOddsFreshness()`) reading `max(fetched_at)` from `cached_extended_odds`; surface it as a second field on the status loader (e.g. extend `getOddsStatus` or add a sibling `getArbOddsStatus`) so the second status-bar line can read "Spreads & totals not fetched yet" (null) vs. an age string using the same `describeOddsAge` helper and the same 2-hour amber threshold already built for moneyline (D-16 explicitly reuses that threshold).

### Anti-Patterns to Avoid
- **Adding a `market_group` column to `cached_odds` instead of a new table:** touches the finder's proven WR-01 code path for no benefit — see Alternatives Considered.
- **Picking each arb side's independently-best price and only demoting the loser on a same-book collision:** can produce a worse (or missed) arb than the true best cross-book pair — use the explicit pair search (Pattern 1).
- **Treating a whole-number spread/total line as eligible:** a whole-number line (e.g. exactly -3 or exactly 44) carries push risk; D-08 requires half-point lines only — filter these out entirely before pairing, not just flag them.
- **Reusing `purgeUnrefreshedEvents`/`purgeStartedEvents` across both tables from one call site:** would silently violate D-16's "normal refresh does not clear them" the first time someone "simplifies" the refresh orchestration to share a helper.
- **Rounding both arb legs by re-deriving `stakeB = total − stakeA_rounded`:** D-02 says "each leg is rounded to whole dollars" independently, and "the display shows the exact resulting worst-case profit" — round each leg's own exact fractional stake independently (Pattern in `## Arb Math`), don't force the pair to re-sum to the entered total.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| American↔decimal odds conversion | A second conversion helper for arb math | `src/domain/hedge/americanOdds.ts`'s existing `americanToDecimal` (precision-40 clone) | Same single-source-of-truth rationale as Phase 1 — a second implementation risks a rounding-mode/precision mismatch between the finder and the arb tab |
| Cent/whole-dollar rounding-candidate selection | A new ad-hoc rounding scheme for two independent legs | Generalize `bonusBet.ts`'s "compute all rounding candidates, pick whichever maximizes the guaranteed minimum" pattern to 2×2 (or fewer, deduped) candidates for two independently-rounded legs | The existing pattern is already fixture-tested and battle-tested for the exact "which rounding direction protects the guaranteed floor" question this phase re-asks with one more variable |
| Credit-quota tracking for the new fetch | A second credit ledger or a `market_type` column on `credit_usage` | The same `credit_usage` table/`recordCreditUsage`/`getLatestCreditUsage` already used by `refreshOdds` | There is exactly one Odds API account and one shared monthly balance — splitting it into two ledgers would require reconciling them back into one number for the credit meter anyway |
| Half-point line matching | A generic "fuzzy" price/line matcher | An exact-equality match on `point` (spreads: `pointA === -pointB`; totals: `pointA === pointB`) plus a half-integer filter (`Math.abs(point % 1) === 0.5`) | D-08 explicitly requires exact matching, not nearest-line matching — a fuzzy matcher would silently reintroduce push risk across slightly different lines |

**Key insight:** every "don't hand-roll" item here is really "don't fork a Phase 1 module" — this phase's entire domain-logic surface is a generalization of four already-correct, already-tested Phase 1 functions, and the failure mode to avoid is drift between the finder's and the arb tab's independently-maintained copies of the same math.

## Arb Math

Given two decimal odds `Da`, `Db` (from `americanToDecimal`) and a user-entered total stake `S`:

```
pA = 1 / Da,  pB = 1 / Db
impliedSum = pA + pB              // < 1 required for a true arb (D-04/D-05)
stakeA_exact = S * pA / impliedSum
stakeB_exact = S - stakeA_exact   // exact split of the entered total
payoutA = stakeA_exact * Da
payoutB = stakeB_exact * Db       // equal to payoutA in exact (unrounded) math
profit_exact = payoutA - S
returnPct_exact = profit_exact / S * 100
```

**Rounding (D-02), generalizing `bonusBet.ts`'s candidate-and-maximize pattern to two independently-rounded legs:**

```typescript
// Source: generalization of src/domain/hedge/bonusBet.ts's rounding-candidate pattern
function roundingCandidates(exact: Decimal, dp: number): Decimal[] {
  const down = exact.toDecimalPlaces(dp, Decimal.ROUND_DOWN);
  const up = exact.toDecimalPlaces(dp, Decimal.ROUND_UP);
  return down.equals(up) ? [down] : [down, up];
}

function splitArbStake(
  stakeAExact: Decimal, stakeBExact: Decimal,
  oddsA: Decimal, oddsB: Decimal,
  precision: "whole" | "cents",
) {
  const dp = precision === "whole" ? 0 : 2;
  let best: { stakeA: Decimal; stakeB: Decimal; guaranteedProfit: Decimal } | null = null;

  for (const stakeA of roundingCandidates(stakeAExact, dp)) {
    for (const stakeB of roundingCandidates(stakeBExact, dp)) {
      const totalLaid = stakeA.plus(stakeB);
      const netIfAWins = stakeA.times(oddsA).minus(totalLaid);
      const netIfBWins = stakeB.times(oddsB).minus(totalLaid);
      const guaranteedProfit = Decimal.min(netIfAWins, netIfBWins);
      if (!best || guaranteedProfit.gt(best.guaranteedProfit)) {
        best = { stakeA, stakeB, guaranteedProfit };
      }
    }
  }
  return best!; // candidates always non-empty
}
```

This is the same "try floor/ceil, keep whichever maximizes the guaranteed minimum" discipline as `bonusBet.ts`, extended from one rounded variable to two independent ones (whole-dollar mode: up to 4 candidate pairs, deduped; exact-cents mode: usually 1, rarely up to 4). Follow `bonusBet.ts`'s `clean()` 20dp-snap-before-2dp-round step for the same reason (American-odds decimal conversions carry unavoidable base-10 truncation noise from `-300`/`-275`-style prices that must not leak into a cent/dollar rounding decision).

**Return % rounding:** follow the established Phase 1 convention (`conversionPct` in `bonusBet.ts` uses `ROUND_DOWN`) — never overstate a displayed guaranteed number. `returnPct = guaranteedProfit.dividedBy(totalStakeActuallyLaid).times(100).toDecimalPlaces(2, Decimal.ROUND_DOWN)`, where `totalStakeActuallyLaid = stakeA + stakeB` (the real rounded total, which may differ slightly from the user's entered value in whole-dollar mode — the expanded row shows the true per-leg stakes per D-10, so this is visible, not hidden).

**Reference fixture to write (mirrors Phase 1's fixture-first testing style):** e.g. Book A +120 (Da = 2.20), Book B −105 (Db ≈ 1.952381), S = $200 whole-dollar mode → `impliedSum = 1/2.20 + 1/1.952381 ≈ 0.454545 + 0.512195 = 0.966740 < 1` (a real ~3.3% arb) → `stakeA_exact ≈ 94.03`, `stakeB_exact ≈ 105.97` → round to $94/$106 or $94/$107 etc., pick whichever whole-dollar pair maximizes the guaranteed minimum. Compute exact numbers in the test, don't hand-copy this approximation.

## Market Filter: Spreads & Totals

**Odds API response shape** [CITED: the-odds-api.com/liveapi/guides/v4/, WebFetch 2026-09-25]: spreads/totals outcomes carry a `point` field alongside `name`/`price`, e.g. `{"name": "Dallas Cowboys", "price": -109, "point": 6.5}` for a spread, and `{"name": "Over", "price": ..., "point": 44.5}` for a total. `src/domain/odds/schemas.ts`'s `OddsOutcomeSchema` must add `point: z.number().optional()` (h2h outcomes omit it) — this is additive and backward-compatible with the existing `z.looseObject` usage; without it, `point` would be silently dropped from the typed result even though the raw JSON has it, since `looseObject` preserves unknown keys at the object level but doesn't give them a typed accessor.

**Half-point filter:** a line is push-risk-free (D-08) only when its fractional part is exactly `.5`. Since half-integers (`x.5 = x + 1/2`) are exactly representable in IEEE-754 binary floating point (unlike money's base-10 fractions), a plain `Math.abs(point % 1) === 0.5` check is safe here — no decimal.js needed for this specific check (it is a line identifier, not a money amount).

**Matching rule (D-08):**
- **Spreads:** for a given event, group quotes by `Math.abs(point)` (the line magnitude). Within a group, the "positive side" is whichever team has `point > 0` and the "negative side" has `point < 0`. Only pair a positive-side quote from one book with a negative-side quote from another book **at the same magnitude** — do not pair, e.g., a −3.5 quote from one book with a +4.5 quote from another (different magnitudes are not "the same line," per D-08's literal wording).
- **Totals:** group by the exact `point` value (Over and Under always share the same point at a given book, and typically across books too, since alternate lines are a separate, unrequested market). Pair the best "Over" quote with the best "Under" quote at that exact point value, across different books.
- **One row per line, not per market:** since D-07 says "one row per game and market" and the market badge shows the specific line (e.g. "Spread +3.5", "Total O/U 44.5"), treat each distinct qualifying line as its own row — a game can produce multiple spread/total rows if multiple point values each independently clear the arb bar (uncommon in practice, since books mostly agree on a single spread/total per game, but must be handled for the rarer case of a book quoting an unusual local number).

```typescript
// Source: sibling to src/domain/hedge/marketFilter.ts's extractTwoWayMoneylines, generalized for
// spreads/totals point matching per D-08
export interface LineQuote { bookKey: string; side: "positive" | "over" | "negative" | "under"; team: string; oddsAmerican: number }
export interface TwoWayLineMarket {
  eventId: string; sportKey: string; commenceTime: Date; homeTeam: string; awayTeam: string;
  marketType: "spread" | "total";
  line: number; // magnitude for spreads, exact point for totals
  quotes: LineQuote[];
}

function isHalfPoint(point: number | undefined): point is number {
  return point !== undefined && Math.abs(point % 1) === 0.5;
}
```
(Full extraction loop mirrors `extractTwoWayMoneylines`'s event/bookmaker/market iteration, grouping by `(eventId, marketType, line)` instead of just `eventId`.)

## Common Pitfalls

### Pitfall: Changing `cached_odds`'s primary key to accommodate a market-group column
**What goes wrong:** Adding `market_group` as part of a composite primary key on the existing, populated `cached_odds` table requires backfilling every existing row with a default group value and touches a constraint the finder's `getCachedEvents`/`replaceSportOdds` already depend on being `eventId`-keyed.
**Why it happens:** It looks like the "obvious" minimal-diff way to add a second dataset to the same table.
**How to avoid:** Use a separate table (`cachedExtendedOdds`) instead — see Architecture Patterns Pattern 3's Alternatives Considered entry. Zero existing Phase 1 code needs to change.
**Warning signs:** A migration that includes `ALTER TABLE cached_odds DROP CONSTRAINT ... ADD PRIMARY KEY (event_id, market_group)`.

### Pitfall: Book-pair collision silently producing a suboptimal or missing arb
**What goes wrong:** If arb-pairing reuses the finder's "each side's independent best price" pattern, a game where the same book (e.g. DraftKings) happens to offer the best price on *both* sides will either (a) incorrectly get demoted on only one side even when swapping would find a better pair, or (b) in a naive implementation, get skipped entirely as "no valid different-book pair" when a valid, if slightly less optimal, pair does exist.
**Why it happens:** The finder's existing pattern is correct *for the finder* (bonus book is fixed input, not derived), and it's tempting to reuse it verbatim.
**How to avoid:** Implement the explicit O(n²) book-pair search from Pattern 1.
**Warning signs:** A function named `bestArbSide` (singular, one side at a time) instead of `findBestArbPair` (both sides evaluated jointly).

### Pitfall: A normal refresh accidentally purging the spreads/totals cache
**What goes wrong:** If `runOddsRefresh`'s existing `purgeUnrefreshedEvents(now)` call (which deletes any `cached_odds` row with `fetched_at` older than the just-completed refresh) is ever pointed at a shared table or a shared purge helper is refactored to run against both tables, spreads/totals data disappears on the very next ordinary "Refresh odds" click — directly violating D-16.
**Why it happens:** Purge logic looks generic/reusable at a glance.
**How to avoid:** Keep purge functions table-scoped and call sites separate — the normal refresh path (`refresh.ts`) must never import or call anything from the new `refreshExtended.ts`/extended-table store functions, and vice versa.
**Warning signs:** A shared `purgeStale(table, now)` helper being called from both `runOddsRefresh` and `runSpreadsTotalsRefresh` in the same code review — not wrong in principle, but re-verify each call site's table argument carefully if this refactor happens.

### Pitfall: Treating a whole-number spread/total line as matchable
**What goes wrong:** A book quoting a whole-number line (e.g., exactly `-3` or exactly `44`) carries real push risk (the favorite wins by exactly 3, or the total lands exactly on 44) — including it in arb pairing could produce a "profit" figure that's actually a $0 push scenario on one leg while the other leg is a real cash loss (asymmetric, unlike the NFL moneyline tie case, which is symmetric and harmless).
**Why it happens:** It's easy to only check "is this a two-outcome market" and forget the half-point constraint.
**How to avoid:** Filter with `isHalfPoint(point)` before any pairing logic runs, for every spread/total outcome, not just after computing candidate pairs.
**Warning signs:** A test fixture using round-number spread/total values (e.g. `point: -3` or `point: 44`) that doesn't assert the row is excluded.

### Pitfall: Odds-age status loader recomputing "spreads/totals age" from a query with no rows
**What goes wrong:** Before the user ever presses "Search spreads & totals," `cached_extended_odds` is empty; a naive `max(fetched_at)` query returns `null`, which must map to the UI-SPEC's specific "Spreads & totals not fetched yet" copy — not to "0 minutes ago" (which a careless `describeOddsAge(null, now)` call, or a fallback to `new Date(0)`, could produce).
**How to avoid:** `getExtendedOddsFreshness()` returns `Date | null` exactly like the existing `getOddsFreshness()`, and the status loader/UI must explicitly branch on `null` (this is exactly the existing `oddsFetchedAt === null` handling already proven in `find-hedges.ts`/`FinderScreen` — reuse the pattern, don't reinvent it).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| A second, uncoordinated credit-tracking path drifting from the real Odds API balance | Tampering (of trusted data) | `refreshSpreadsTotals` must write to the *same* `credit_usage` table/functions as `refreshOdds` — never a parallel ledger (see Don't Hand-Roll) |
| Extended-fetch request exhausting the shared monthly credit budget faster than expected (3× cost per press) | Denial of Service (of the shared credit resource) | Same `evaluateRefreshGate`/warn-100/block-20 thresholds apply unchanged; the confirm dialog must show the real, dynamically-computed 3× estimate (D-14), never a hardcoded "12 credits" |
| Malformed/missing `point` field on a spreads/totals outcome silently corrupting line-matching | Tampering (of trusted data, not necessarily malicious) | `point: z.number().optional()` on the schema plus an explicit `isHalfPoint()` guard before any pairing logic — treat a missing/invalid `point` as "not eligible," never coerce or default it |
