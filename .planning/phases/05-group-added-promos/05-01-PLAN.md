<objective>
Phase goal (user story):

**As a** group member, **I want to** add a promo I see in my own sportsbook app and manage the ones I added, **so that** my Promos list and Opportunities feed include the promos the scrapers miss, with the same exact hedge math, visible only to me.

This plan lays the privacy boundary every later slice relies on: one owner column on `promos` (generated migration, applied in Plan 03 with the owner's OK), a single visibility choke point in `getActivePromos` (secure by default: no viewer = scraped only), a new `any` scope for unrestricted bonus bets (A2), the `deleted` status for soft delete (D-11), and a guard so scraper runs never expire hand-added promos (Research Pitfall 4).

Purpose: PROMO-02 (personal only, D-01) and the storage shape PROMO-01 needs.
Output: schema + migration files, visibility helpers with SQL-shape tests, `any` scope, scraper guard with regression test.

DO NOT USE THE APP MANUALLY UNTIL PLAN 03 APPLIES THE MIGRATION: after this plan, `getActivePromos` (and, after Plan 02, the feed/tracking queries) select `added_by_user_id`, a column that does not exist on the live Neon DB until Plan 03's owner-approved `npm run db:migrate`. Until then the Promos and Opportunities screens will error. Automated tests are unaffected (they mock the db / check SQL shape). Do not run the dev server against the live DB or deploy between this plan and Plan 03.

Orchestrator default A2 (visible at execution): unrestricted bonus bets are stored as `scope_kind='any'` with a new PromoScope kind `{ kind: "any" }` (Research Pattern 4). The owner did not answer this explicitly.
</objective>
