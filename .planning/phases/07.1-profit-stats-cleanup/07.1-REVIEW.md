## Warnings

### WR-01: Group (Statistics) observations are ranked at the viewer's precision, not "whole"

**File:** `src/app/actions/get-opportunities.ts:58-60`, `src/app/actions/get-promos.ts:140`
**Issue:** Both server actions pass the member's view precision (`precision`) to `recordCurrentProfitObservations`. The scheduled job calls it with no precision, so `"whole"` is used (`promoObservations.ts:142`). `recordProfitObservations` upserts with `greatest(...)`. A member who views in cents therefore writes cents-precision numbers into `promo_profit_observations`, and the daily max that the Statistics tab reads (`profitHistory.ts:12`) then depends on who opened which screen at which precision. This is the WR-01 problem the phase fixed for member recording, still present for group recording. This phase rewrote these calls and left the precision argument in place.
**Fix:** Group recording should always rank at whole precision. Drop the argument at both call sites, or remove the `precision` option from `recordCurrentProfitObservations` entirely:
```ts
await recordCurrentProfitObservations(now, {
  activePromos: ctx.activePromos,
  cached: { ... },
}); // computeCurrentProfitEntries defaults to "whole"
```

### WR-02: Dashboard and Promos loads write the viewer's private promos into the site-wide Statistics table

**File:** `src/app/actions/get-opportunities.ts:59`, `src/app/actions/get-promos.ts:140`, `src/db/promoObservations.ts:114`
**Issue:** `ctx.activePromos` and `activePromos` in getPromos come from `getActivePromos(now, userId)`, which includes promos the viewer added privately (`promoVisibilityCondition(viewerUserId)`, `promos.ts:304-307`). The scheduled job calls `getActivePromos(now)`, which returns public promos only. Before this phase, `getProfitObservationsSince` filtered its reads by the viewer's visibility. That reader has been deleted, so the only remaining reader is `loadDailyProfitHistory` (`profitHistory.ts:12-26`). It has no visibility filter and feeds the site-wide Statistics tab.

The effect: a member's private promo appears in everyone's Statistics, but only on days that member opened the Dashboard or Promos tab. The data is inconsistent and leaks between members. The bug existed before this phase, but the phase removed the last viewer-filtered reader and rewired these exact calls.
**Fix:** Pass only the group-visible promos to the group recorder:
```ts
activePromos: ctx.activePromos.filter((p) => !p.addedByYou),
```
Do the same in getPromos. Alternatively, have `loadDailyProfitHistory` join on `promos.addedByUserId IS NULL`.

### WR-03: The member recording rule is still written twice, so the scheduled job can drift from the Dashboard

**File:** `src/ingestion/odds/morningObserve.ts:58-76`, `src/db/memberFeedRecording.ts:9-17`
**Issue:** `memberFeedRecording.ts` calls itself "THE member recording rule", but `recordAllMembersObservations` still calls `computeMemberFeed`, `buildMemberObservationEntries` and `recordMemberProfitObservations` inline. It gets whole precision only indirectly, because it passes `precision: "whole"` to `loadMemberFeedContext`. If the helper changes (another precision override, an entry filter), the scheduled job will silently stop matching the Dashboard, which is the consistency this phase was meant to guarantee.
**Fix:** In the morning job, call the shared helper:
```ts
const ok = await recordMemberFeedObservations({
  userId: id, now, feedPromos: ctx.feedPromos, rankOpts: ctx.rankOpts, userBookSet: ctx.userBookSet,
});
```
Then update the helper's doc comment to name all three callers.

### WR-04: The member pass and the snapshots are skipped entirely when no Odds API key is configured

**File:** `src/ingestion/odds/morningObserve.ts:98-100`
**Issue:** `runMorningObservation` returns `skipped: missing-api-key` before any recording happens. The group recorder, the snapshot recorder and `recordAllMembersObservations` all read cached odds only and need no key. If the key secret is missing or rotated out, every scheduled run records nothing for anyone, and the run still exits 0 with only a log line. That contradicts the W1 guarantee ("the morning job always runs the member pass"). The docstring says recording should happen "even when the refresh itself was blocked/busy/errored".
**Fix:** Gate only the refresh on the key, and always run the recorders:
```ts
const refreshOutcome: RefreshOutcome = hasApiKey
  ? await runOddsRefresh({ confirmed: true, triggeredByUserId: null, now })
  : { status: "error", message: "missing-api-key" };
// ...recorders + member pass unchanged
```
Alternatively, keep the skip status but run `recordAllMembersObservations` before returning it.

**Fix:** Trim the header to describe the date helpers. Optionally move `ProfitObservation` next to `recordProfitObservations`.

### IN-03: getPromos' group recorder still reads both odds caches and the book list a second time

**File:** `src/app/actions/get-promos.ts:140` vs `157-168`
**Issue:** The W2 fix (`cached` input) was applied only to the Dashboard. On the Promos tab, the group recorder runs before the action loads the caches, so each load reads `getCachedEvents`, `getCachedExtendedEvents` and `getHedgeBookKeys` twice. A refresh landing between the two reads can record numbers from a different snapshot than the one shown. These reads are not new and cost no API credits.
**Fix:** Move the call after the cache load and pass `cached: { moneylineEvents, extendedEvents, oddsFetchedAt, everyUsableHedgeBookKeys: await getHedgeBookKeys() }`. Keep a separate call for the `feedPromos.length === 0` branch.

### IN-04: Redundant try/catch around recorders that cannot throw, and the call sites are inconsistent

**File:** `src/ingestion/odds/morningObserve.ts:105-115`, `src/app/actions/get-opportunities.ts:57-70`
**Issue:** Both recorders now catch everything themselves. The outer catches cannot fire, and `get-promos.ts:140` has no such wrapper, so readers get mixed signals about the contract. This is harmless but adds noise.
**Fix:** Pick one convention: remove the outer catches, or add one in getPromos with a short comment.

### IN-05: The new tests spy on `console.error` without restoring it

**File:** `src/app/actions/get-opportunities.test.ts:560,572`
**Issue:** `vi.spyOn(console, "error").mockImplementation(...)` is never restored, and `vitest.config.ts` does not set `restoreMocks`. Every later test in the file runs with `console.error` silenced, which hides unexpected errors while debugging. The tests in `memberFeedRecording.test.ts` and `morningObserve.test.ts` do restore their spies.
**Fix:** Keep the spy and call `spy.mockRestore()` at the end of the test, or add `afterEach(() => vi.restoreAllMocks())`.
